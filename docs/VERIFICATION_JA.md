## 1. 前版（AUDIO_REVISION_EXEC_FIXED）の原因調査

| 症状 | 原因 | 確かさ |
|---|---|---|
| **HTTP 503** | 既定の KiwiSDR `kiwisdr.areg.org.au:8073` は、認証送信後 10 秒応答せず切断した（再接続を繰り返す）。KiwiClient の rigctl（6400番）は**接続中の受信ループの中でしか処理されない**ため、ポートは開いているのに無応答になり、bridge の 2 秒タイムアウト → 503。 | **実測**（`F 10010000` を送ると 2.0 秒でタイムアウトを再現。同梱 kiwi ライブラリは本家と同一でクライアントの不具合ではない） |
| 音が出ない | 上記で KiwiSDR に繋がっていない（受信音声が 0 ブロック）。 | **実測**（同条件のログ） |
| 周波数コマンド `M AM 0` | 通過帯域 hc=0 を渡す不具合。 | コード読解で確認（実機では未再現） |
| VOL 70 のまま変わらない／HTTP -11 | bridge は 1 本のロックで全要求を直列化。tune が rigctl 待ち(2 秒)でロックを握る間、音量要求が待たされ、ADV の 2.5 秒タイムアウトで失敗 → 表示が更新されない。ADV は tune を 250ms ごとに再送するため悪化。 | **推定**（実機で未再現。ただし構造上起こり得る） |
| 「Connected」 | 「Mac の HTTP が最後に 200 を返した」だけの意味で、KiwiSDR 接続とは無関係だった。 | コード読解 |
| HTTP -1 / -11 | ESP32 HTTPClient の定義で -1=接続拒否(Mac側が待ち受けていない/IP・FW)、-11=読み取りタイムアウト。 | ライブラリ定義 |
| 画面が最大 2.5 秒固まる | HTTP が UI ループ内の同期処理。 | コード読解 |
| 配布物 | `Start RADIO DAYS Mac.command` は ZIP 内で 755（確認済み）。ただし未使用の Windows DLL 等 約 4MB を含んでいた。 | ZIP 一覧で確認 |

## 2. 今回の変更

- Mac 側を 1 プロセスに作り直し（`mac/radiodays_sdr.py`）。rigctl・JSON ファイル経由の音量・別プロセスを廃止。
  周波数/モード/音量はメモリ上の値。KiwiSDR 状態は `/state` の `link` で返し、HTTP 503 を返す経路はありません。
- KiwiSDR 接続失敗（無応答・拒否・満員）は 2 回で自動的に次のサーバーへ切替。
- 実受信強度(RSSI→S)と実出力レベルを `/state` で提供。
- ADV 側: HTTP を別タスク化、絶対値コマンド、Wi-Fi/Mac/Kiwi を区別した状態表示、U135・キー処理と Wi-Fi 画面は U10 から移植。

### 6.3 Mac 側の変更と自動テスト
- `/servers` に `lat` / `lon` を追加（無ければ null）。`/server?index=N` は**要求直後の `/state` に即反映**（`server_index=N`, `link=connecting`）。ブロック中の接続・待機は socket を切って即中断（以前は最大 8 秒待ちだった）。切替要求後に古い受信機の音声は流しません。
- 自動テスト **12 件 OK**（追加: 緯度経度の存在・範囲・Ironstone 同一地点、切替の即時反映、範囲外 index=400、**接続失敗の報告と自動切替で index が進む**、**応答しないサーバーからの切替中断（3 秒以内）**）。
- **実 KiwiSDR での通し試験**（`tests/live_switch.py`。ファームと同じ `/servers`→`/server?index=`→`/state`）: Rotorua、AU2 は要求どおり受信中。Ironstone AU は受信機側が `No multiple connections from the same IP address` で拒否→Mac が AU2 へ**自動切替**、Osaka は 2 回タイムアウト→Rotorua へ自動切替。いずれも `/state` は要求直後 `connecting`、最終的に実際に繋がった受信機の index と `connected`（音声ブロック受信）を返した。**この試験中は別の Mac プログラムも同じ IP から接続しており、拒否・タイムアウトの一部はそれが原因の可能性があります**。

### 10.2 KiwiSDR の RSSI は AUTO 選局に使えるか（実測）
実際の KiwiSDR（Ironstone AU2、Rotorua NZ）に接続して測定しました（2026-10-24 夜、Mac の Wi-Fi 経由）。

| 項目 | 実測値 |
|---|---|
| RSSI の取得 | 音声ブロックごとに 1 個（dBm）。**ブロックは 2048 サンプル（約 171 ms）、毎秒約 5.85 ブロック**。追加の通信は不要（受信中の音声に付いてくる） |
| 周波数を変えてから**有効な値**が来るまで | コマンドが届いて 0〜170 ms 後に Kiwi が適用し、**新しい周波数の最初の有効な値は約 0.65〜0.9 秒後**（古い周波数の値が 4〜5 ブロック残る）。強い局(−66 dBm)と雑音(−111 dBm)を交互に 10 回切り替えて、遷移がブロックの境目で起きることを確認 |
| 雑音床 | 約 −110 dBm（31m 帯、100 点の中央値 −105、下位 25% が −109）。局は雑音床より 15〜45 dB 強い（−95〜−65 dBm）。搬送波は 5 kHz 間隔で、**±5 kHz 隣では 20 dB 以上落ちる**（`9495:-94, 9500:-75, 9505:-111`）ため 5 kHz 刻みで局を見分けられる |
| 1 ステップの所要時間 | 待ち 0.95 秒 + 測定 2 ブロック ≒ **1.4〜1.5 秒**（実際のスキャンでの平均。山の追跡・再確認を含む区間も 1.4〜1.7 秒/測定）。100 kHz（20 ステップ）で約 30 秒 |
| 通信負荷 | KiwiSDR への追加は周波数変更の小さな 1 メッセージのみ（約 1 回/1.5 秒）。Mac–Cardputer 間はスキャン中だけ状態取得を 0.7→0.2 秒間隔にする（数 KB/s） |
| 周波数範囲 | 10〜30000 kHz（Kiwi の帯域）。端で `END OF BAND` |

**結論:** 受信強度（RSSI）による停止判定は、**実用的な信頼性で成立します**。ただし**探索は 1 ステップ約 1.4 秒**と遅い（Kiwi が新しい周波数の音声を送ってくるまでの遅延による物理的な限界）。1 MHz を端から端まで探すには約 5 分かかります。より速くするには KiwiSDR のウォーターフォール（スペクトル）ストリームを使う方法がありますが、受信機側の接続数制限（同一 IP からの二重接続を拒否する受信機がある）の問題があり、今回は採用していません。

### 10.3 停止判定の設計と根拠
単純な強度の大小だけでは雑音・混信にも反応するため、次の組み合わせにしました（定数は `radiodays_sdr.py` の `SCAN_*`）。
1. **雑音床との差**: 直近 20 回の測定の下位 20%（局が混じっても動きにくい）を雑音床とし、**+12 dB 以上**で候補。起動直後の 3 回は雑音床の推定にだけ使う（暖機）。
2. **測定は 2 ブロックの小さい方**: 雷などの一瞬のノイズは 1 ブロックしか持続しないので無視される。
3. **山の頂点を追う**: 候補から先へ、上がっている間は進み、下がり始めたら（最大 3 ステップ先まで）最大の周波数に**戻る**。
4. **再確認**: 頂点で新しく測った 3 ブロックの**中央値が +10 dB 以上かつ最小が +6 dB 以上**。満たさなければ誤警報として探索を続ける。
5. **再始動**: 局の上や裾野から始めたときは、雑音に戻る（+6 dB 未満）まで検出を無効にして、同じ局にすぐ止まらないようにする。
6. 刻みは **5 kHz 以上**（短波放送の間隔。STEP が 0.1/1 kHz でも 5 kHz に格子合わせ）。

## 20. 通常画面の再配置と Cardputer 音声タイムアウトへの防御修正（ファームウェア v1.10、2026-10-25）

### 20.1 利用者から報告された現象

OUT ADV で再生中、PC 側 Terminal に次の順で記録されました。

- 07:29:34 `Broken pipe`、約0.5秒後に再接続。
- 07:53:31 `Broken pipe`、直後に再接続。
- 07:54:38 `Cardputer audio connection lost: timed out`。提示された範囲には、その後の再接続記録がない。

この記録から確認できるのは、最後の時点で **PC から Cardputer への音声送信がタイムアウトしたこと**です。Cardputer が音声 TCP を読み取らなくなった理由は、このログだけでは特定できません。Wi-Fi、Cardputer のタスク停止・処理遅延、PC 側、その他の要因のどれかを断定していません。

### 20.2 防御修正

- Cardputer の音声受信で、読み取り失敗・プロトコル異常・無データ監視の各経路から、必ず再接続状態へ移りソケットを閉じるよう明示。
- 音声受信タスクの優先度を 1 から 2 に上げ、同じコア上の通常ネットワーク処理に埋もれにくくした。
- PC 側の送信ソケットに TCP keepalive を設定（OS が対応する細かな設定は安全に試し、未対応なら無視）。
- PC 側の送信タイムアウトを 3 秒から 8 秒へ変更。短い処理停滞で PC が Cardputer より先に切断する可能性を減らした。

これらは再接続しやすくする防御策です。原因を特定した修正ではなく、実機で再発しないことを保証しません。

### 20.3 通常画面の確定仕様

**2026-10-25、利用者が240×135実寸プレビューを確認し、以下をv1.10の確定デザインとして承認した。** 以後の変更は、Cardputer ADV実機で判明した可読性・発色上の微調整、または利用者との再協議によるものに限る。これはPC上のプレビュー承認であり、実機表示の確認ではない。

- 左上: 白い盤面の、背を低くした横長`SIGNAL` / `VOLUME`アナログ針メーター。黒い縁は原則1pxとし、盤面の上辺・左辺内側へ灰色の影を入れて、厚い黒枠ではなく金属面へ沈んだ表示にした。
- 右上: タイトルと横方向に重ならないため、1行下げず画面上端へそろえた角丸の白い凹型パネル。5段表示は上から`OUT PC / OUT ADV`、`WiFi / PC / Kiwi`、`MANUAL / AUTO`、`AM / USB / LSB`、`.1 / 1 / 5 / 10 kHz`。5行を等高にし、各行の間を1pxの薄い灰色線で分離。M5Stackの裏面印刷を意識して文字を青・緑・橙・赤・紫に色分けした。通信LEDの緑・黄・赤という状態の意味と、その他の選択中アンバーは維持。
- 中段: 横幅いっぱいのチューニング目盛り。中央の赤線は固定し、目盛りが動く。上段下の空白を減らすため上へ詰め、黒い縁は1pxとした。
- 下段: 黒地・蛍光緑のESP32風液晶を2個の独立した窪みへ分離。チューニング目盛りとの間隔を約半分へ詰め、34px高の表示面と、その上下に同じ高さの銀色レールを確保した。左は大きな液晶電卓風7セグ周波数（小さな通常文字の`kHz`）と状態行で、外側ベゼルの上4本・下4本のねじで固定。右は上段に曜日・日付・小さな`JST`、下段に同じ7セグ様式の時刻を置くG-SHOCK風の情報階層とし、上2本・下2本のねじを液晶面の外側へ配置した。同期前はプレースホルダーを表示し、NTP失敗はラジオ動作を止めない。
- `STEP`という語は通常画面から外した。モード変更時はAM=5 kHz、USB/LSB=1 kHzへ自動設定し、その後は1〜4キーで変更できる。同じモードをもう一度押しただけでは利用者の刻み幅を上書きしない。
- 銀色の金属パネル、立体的な凹みと影、地球儀画面の衛星アニメは維持。

プレビューは実際の描画コードから生成し直し、`docs/preview/`（4倍）と `docs/preview/actual_size/`（240×135実寸）へ保存しました。

### 20.6 Launcherの`Fail3`とサイズ互換版（2026-10-25）

利用者がアプリ`.bin` 1,321,456 B（SHA-256 `970cd9b4...`）をLauncherのWi-Fi経由で導入したところ、`Fail3`となり書き込めなかった。これはv1.9で発生した`Fail 376: 3`と同系統と考えられるが、Launcher側の詳細な失敗理由は表示だけでは断定できない。

画面・操作ロジックを変えず、フラッシュ上だけに置く3,072 Bの不活性なサイズ互換パッドを追加した1,324,592 B版も、利用者のLauncherで再び`Fail3`となった。これにより「特定のファイルサイズだけが原因」という仮説は棄却した。古いLauncherソースでは`Update.end()`失敗時に`Update.getError()`を表示し、Arduino ESP32のエラー3は`UPDATE_ERROR_READ`（書き込み先イメージを起動可能と確認する段階の読み取り／検証失敗）である。利用者のLauncher版を特定していないため完全に同じ経路とは断定しないが、少なくともフォント用メモリ不足を直接示す番号ではない。

利用者の希望によりパッドを撤去し、周波数と時刻の両方を大きく太い組み込みビットマップ文字へ戻した。直前版で時計7セグを残したのは依頼との不一致だったため訂正した。現行`.bin`は1,321,088 B、SHA-256 `e42ef9f4180437c995db201ba2c74a1483ff106a80ed1b3624d87eb185de4db8`。ESP32-S3イメージのchecksumとvalidation hash、配布ファイルのSHA-256を確認し、PC上の描画91項目も失敗0。旧版との取り違え防止用に、同一内容の`RDSDR_v110_BOTH_BOLD.bin`もローカルに作成した（公開対象外）。

利用者がこの明示名ファイルをLauncherのWi-Fi経由でインストールし、**導入成功・起動・正常動作**を報告した（2026-10-25、Cardputer ADV実機）。周波数だけ通常文字へ戻し時計7セグを残した直前版は`Fail3`、両方の7セグ描画を外した版は成功したため、失敗条件は時計側を含むカスタム7セグ描画コード、またはそれによって生成されるバイナリ配置に関連していた可能性が高い。ただし、コード内容そのものとバイナリ配置のどちらがLauncherの検証失敗を起こしたかまでは特定しておらず、「フォント用RAM不足」とは断定しない。
